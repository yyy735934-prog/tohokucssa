# “组个局”MVP 产品规格（讨论稿）

更新日期：2026-08-24

## 1. 产品目标

“组个局”用于组织频率较高、安排相对灵活的日常活动。活动可以先发布参与意向，再根据人数决定是否成行；它与现有需要完整时间、地点和审核流程的正式活动并行存在。

首版需要跑通以下闭环：

1. 管理员确认可自动发布的每周活动。
2. 系统按周批量创建并开放“组个局”。
3. 成员使用 Google 登录后报名。
4. 系统显示距离成局还差多少人，并处理拼车候补。
5. 达标后由主理人或管理员确认最终安排。
6. 未达标活动在周五自动取消并发送通知。
7. 活动现场签到，结束后记录出席情况。

## 2. 已确认的产品规则

### 2.1 发布规则

- 每周活动必须先由管理员确认，才能进入自动批量发布计划。
- 唱歌和多人体育活动优先采用每周自动发布。
- 默认每周一 08:00（日本时间）自动发布，周五 18:00（日本时间）判断是否成局。
- 管理员可以为每个模板单独调整发布时间和成局判定时间。
- 自动发布的是管理员维护并启用的“每周活动模板”，不是由系统自由生成活动内容。
- 模板应包含：活动类别、标题模板、活动日期或日期规则、区域、最低人数、最多人数、报名截止时间、是否需要主理人、是否涉及拼车、默认说明。
- 本周实例创建后，管理员仍可修改、暂停或取消，不影响模板本身。
- 已批准模板提供“立即生成本周组局”，用于临时发布和本地/运营验证；同一模板同一周仍只生成一个实例。

### 2.2 登录规则

- 参加“组个局”必须使用 Google 登录。
- 报名、取消报名、查看本人状态和信誉记录均以登录账号为准，不再仅依赖手工输入邮箱。
- 现有正式活动是否继续允许免登录报名，暂不在本规则中变更。

### 2.3 成局规则

- 唱歌：默认最低 4 人。
- 多人体育：默认最低 4 人。
- 沙龙、桌游、观影：默认最低 5 人。
- 徒步、户外：最低人数由活动模板或主理人设置。
- 最低人数和最多人数均可由管理员在模板或本周活动实例中调整。
- 达到最低人数后，活动进入“待确认最终安排”状态，而不是立即视为最终成行。

### 2.4 主理人规则

- 徒步、户外、沙龙、桌游、观影等活动必须绑定主理人。
- 这些活动达到最低人数后，主理人须在 12 小时内确认最终时间、地点和说明。
- 必须有主理人的活动超过 12 小时仍未确认时，系统自动取消。
- 唱歌和多人体育活动允许没有主理人。
- 唱歌和多人体育活动没有主理人时，由管理员确认最终时间、地点和说明。
- 唱歌和多人体育活动超过 12 小时仍未由主理人确认时，转交管理员确认，不自动取消。
- 唱歌和多人体育活动有主理人时，可由主理人确认，管理员保留代为确认和修改的权限。

### 2.5 周五自动取消

- 唱歌和多人体育活动如果在周五判定时仍未达到最低人数，系统自动取消本周活动。
- 自动取消后停止报名，并向已报名成员发送邮件。
- 自动取消不计入成员的取消或缺席记录。

### 2.7 报名锁定

- 活动创建者或管理员可以把正式活动或组局锁定在当前报名人数。
- 锁定只暂停新报名，不删除或改变现有报名、拼车、签到和出席记录。
- 设置了报名上限的活动仍可单独锁定；即使当前为 0 人也可锁定。
- 活动创建者或管理员可随时恢复报名，活动已开始、结束或取消后不再提供该操作。

### 2.6 拼车规则

- 报名时可选择：自行前往、可开车、需要乘车。
- 选择“可开车”时收集车辆说明和可搭载人数。
- 选择“需要乘车”时，在主理人完成分配前显示“乘车候补中”。
- “乘车候补中”的成员不计入有效成局人数。
- 主理人手动把候补乘客分配给司机；管理员可调整分配。
- 分配完成后，乘客状态变为“已安排乘车”，并收到邮件通知。
- 司机只能看到被分配给自己的乘客所必需的联系信息。

## 3. 建议的状态设计

### 3.1 活动状态

| 状态 | 用户看到的文案 | 说明 |
|---|---|---|
| `recruiting` | 组局中 | 已发布，尚未达到最低人数 |
| `arrangement_pending` | 已达标，待确认安排 | 人数达标，等待主理人或管理员确认 |
| `confirmed` | 已成局 | 最终时间、地点和说明已确认 |
| `in_progress` | 进行中 | 已开始签到和活动执行 |
| `completed` | 已结束 | 活动已结束 |
| `cancelled` | 未成局/已取消 | 周五未达标或人工取消 |

### 3.2 参加状态

| 状态 | 用户看到的文案 | 是否占普通名额 |
|---|---|---|
| `joined` | 已参加 | 是 |
| `ride_pending` | 乘车候补中 | 待确认 |
| `ride_assigned` | 已安排乘车 | 是 |
| `general_waitlist` | 人数候补中 | 否 |
| `cancelled_in_time` | 已提前取消 | 否 |
| `cancelled_late` | 临时取消 | 否 |
| `attended` | 已签到 | 是 |
| `no_show` | 未到场 | 否 |

参加记录采用保留历史的方式，不直接删除，以支持候补、取消时间和出席统计。

## 4. 页面与操作

### 4.1 成员端

- 首页增加“正式活动 / 组个局”切换。
- 组局卡片显示：类别、活动周次、区域、最低人数、已确认人数、还差人数、报名截止时间和当前状态。
- 活动详情显示最终安排是否已经确认。
- 报名前先完成 Google 登录。
- 涉及拼车时显示交通选择和相应信息字段。
- “我的”页面显示组局状态、乘车状态、退出入口和最终安排。

### 4.2 主理人端

- 查看本周组局和报名成员。
- 人数达标后收到邮件，并看到 12 小时倒计时。
- 填写并确认最终时间、地点和补充说明。
- 手动分配司机与乘客。
- 活动现场扫码签到或事后补录。

### 4.3 管理员端

- 创建、编辑、启用、暂停每周活动模板。
- 审核模板后允许自动发布。
- 查看本周所有组局及异常状态。
- 代替无主理人的唱歌和多人体育活动确认安排。
- 调整拼车分配、候补顺序和活动状态。
- 查看取消、签到、缺席和自动任务执行记录。

## 5. 自动化流程

### 每周发布

1. 定时任务读取已启用且经管理员确认的模板。
2. 根据模板生成本周活动实例，避免重复创建。
3. 活动进入“组局中”并开放报名。
4. 向主理人或管理员发送本周发布结果。

### 人数达标

1. 每次报名、取消和拼车分配后重新计算有效人数。
2. 达到最低人数后进入“待确认最终安排”。
3. 向应确认的人发送邮件，并记录 12 小时截止时间。
4. 确认后进入“已成局”，通知参加成员。

### 周五判定

1. 对仍处于“组局中”的唱歌和多人体育活动计算有效人数。
2. 未达到最低人数的活动自动取消。
3. 向已报名成员发送未成局通知。
4. 写入自动任务和活动审计记录。

## 6. 首版暂不自动化的内容

- 不由系统强制指定普通参加者成为主理人。
- 不自动计算司机与乘客的最优组合。
- 不公开展示“鸽子”称号。
- 不允许 AI 在没有管理员确认模板的情况下自由创建活动。
- 暂不把活动工作自动派送到未来的派单平台。

## 7. 首版默认边界

- Google 登录要求仅应用于“组个局”，现有正式活动暂时保留免登录报名。
- 迟取消和未到场记录首版仅本人、活动主理人和管理员可见。
- 所有自动发布时间、截止时间和 12 小时倒计时均按日本时间解释和展示，数据库保存统一时间戳。
